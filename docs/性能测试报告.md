# Rainbow Power KubeJS 性能测试报告

- 测试日期：2026-10-25
- 测试对象：`kubejs/` 全部脚本（243 个 JS 文件，约 38,000 行：startup 105 个 / 14,952 行，server 105 个 / 19,420 行，client 33 个 / 3,798 行）
- 测试方式：静态代码分析（事件注册面与热路径逐行审阅）+ 游戏内实测工具（本次交付的 `/perf` 命令）
- 结论先行：**整体代码质量良好**（大部分 tick 处理器有节流与早退），但存在 **3 个高优先级问题**、4 个中优先级问题，修复后服务端高频路径开销可显著下降。

---

## 一、事件注册面统计（性能敏感入口）

| 事件类型 | 注册数 | 说明 |
|---|---|---|
| `PlayerEvents.tick`（服务端） | 13 | 每玩家每 tick 全部执行，是最热路径 |
| `ClientEvents.tick`（客户端） | 9 | 每帧执行 |
| `EntityEvents.hurt` | 11 | 每次伤害事件全部执行，战斗时高频 |
| `ServerEvents.tick` | 2 | 每服务端 tick 执行 |
| `LevelEvents.tick` | 2 | backroom（限维度）、blood_moon（主世界） |
| `NetworkEvents.dataReceived` | 约 8 通道 | 频率取决于客户端发送侧 |

正面结论：绝大多数 `PlayerEvents.tick` 处理器使用了 `everyTicks()`（基于 `entity.age % n`，成本极低）或 NBT 键早退，写法规范。

## 二、高优先级问题（P0，建议立即修复）

### P0-1 宠物系统 AI 目标选择：全量实体遍历 + UUID 字符串比较 ✅ 已修复

- 位置：`server_scripts/pet_system/MobTameServer.js:48`、`MobTameServer.js:69`
- 写法：`mob.level.getEntities().filter(e => e.getUuid().toString() == lastAttackedId)`
- 问题：这是 `NearestAttackableTargetGoal` 的目标选择谓词，**每次 AI 目标搜索都会触发**（每只宠物、比每 tick 更频繁）。每次调用遍历维度内全部已加载实体，并为每个实体分配 UUID 字符串再比较。实体数百只时这是全脚本最大的单项开销，且随实体数线性放大。
- 修复方案（推荐 a）：
  - a. **谓词内直接比较候选目标**，不做全量查找：谓词参数 `t` 就是当前候选实体，等价写法为 `t.getUuid().toString() == lastAttackedId && t.distanceToEntity(mob) <= 15`，O(1) 且无字符串批量分配；
  - b. 比较改用 UUID 对象：`UUID.fromString(lastAttackedId).equals(t.getUuid())`，把字符串转换移出循环；
  - c. "entityRef 找不到时清除记录"的逻辑移到玩家攻击时维护（`EntityEvents.hurt` 已在写这两个键，顺带做过期清理即可）。

### P0-2 客户端调试遗留：每帧输出日志 ✅ 已修复

- 位置：`client_scripts/utils/getUI.js:11`
- 问题：每帧调用 `screen.getClass().getName()` 并 `console.log` 输出。每秒 20 行、每小时约 7 万行日志，造成日志文件膨胀、磁盘 IO 与字符串分配的持续开销（客户端 FPS 也受影响）。
- 修复方案：该文件是调试工具，重命名为 `getUI.js.disabled` 或加默认关闭的开关常量，需要时再启用。

### P0-3 弓箭系统空闲时持续发网络包 + 写 NBT ✅ 已修复

- 位置：`server_scripts/bow/PlayerTick.js:30`（else 分支）
- 问题：玩家**未拉弓**时也每 2 tick 执行 `player.sendData("bow_progress", { progress: 0 })` 和 `persistentData.bowFullyDrawn = false`。每玩家每秒 10 个无用自定义包 + 10 次 NBT 写入，网络与序列化双向浪费（客户端还要接收处理）。
- 修复方案：记录上次发送的 progress，**仅当值变化时发送**；`bowFullyDrawn` 同理仅在 true→false 转变时写一次。

## 三、中优先级问题（P1，建议近期修复）

### P1-1 动力剑：无节流每 tick 读双手物品 NBT ✅ 已修复

- 位置：`server_scripts/power_sword/main.js:106`
- 问题：每 tick 为每玩家执行 2 次 `getItemInHand` + `getNbt()`，无任何节流（相邻模块均为 5~20 tick 节流）。
- 修复方案：加 `if (!everyTicks(player, 5)) return;`（技能 0.25 秒粒度足够），或至少先比 `stack.id` 再读 NBT。

### P1-2 异星陨石：每 tick 读 NBT（有早退但仍每 tick 触碰） ✅ 已修复

- 位置：`server_scripts/alien_meteor/main.js:41`
- 问题：`data.getLong('AlienMeteorUntil')` 每 tick 执行；未激活时开销小，但激活期间脉冲本身 20 tick 一次。
- 修复方案：入口加 `everyTicks(player, 20)`，脉冲逻辑粒度不变。

### P1-3 鸦羽骨哨：每秒全维度全实体扫描 ✅ 已修复

- 位置：`server_scripts/curios_skill_system/Skillwheel.js:688`
- 问题：每 20 tick 遍历 `getAllLevels()` × `getAllEntities()`，并对每实体读 `persistentData.contains(...)`。开销随全服实体总数与个人维度数量线性增长，是最大的周期性扫描。
- 修复方案（任选其一）：
  - a. 扫描周期放宽到 100 tick（5 秒）——传送返回晚几秒无感知；
  - b. 拉入个人维度时把成员实体 UUID 登记到全局表，扫描只查登记列表。

### P1-4 套装系统：每 5 tick 轮询装备 ✅ 已修复

- 位置：`server_scripts/set_system/SetEffect.js:633`
- 问题：`everyTicks(p, 5)` 触发 `pollAndReevaluate`（装备槽扫描 + 套装重评估）。KubeJS 无装备变化事件，轮询合理，但 0.25 秒粒度偏频。
- 修复方案：降到 10~20 tick；或先做"四件装备 id 拼串与上次缓存比较"的廉价判断，无变化即跳过全量评估。

## 五、交付的实测工具：`/perf` 命令（server_scripts/system/perf/）

静态分析定位"哪里贵"，游戏内实测回答"贵多少"。本次已按项目规范新建模块：

| 文件 | 职责 |
|---|---|
| `server_scripts/system/perf/main.js` | 主入口，注册 `/perf` 命令（OP 权限） |
| `server_scripts/system/perf/bench.js` | 微基准：NBT 读写、UUID 字符串转换、AABB 创建、范围/全量实体查询、Item.of 等 10 项操作的单次耗时 |
| `server_scripts/system/perf/monitor.js` | 运行时监控：TPS（tick 差/真实时间差）、全服实体数，每秒采样（JVM 内存指标因类过滤器限制移除，见第八节补记） |
| `server_scripts/system/perf/probe.js` | 埋点工具：`global.perfTime(name, fn)` / `global.perfBegin` / `global.perfEnd`，`/perf stats` 查看聚合 |

用法（进游戏后 `/reload` 生效）：

```
/perf bench            # 微基准（默认轻操作 5000 轮 / 查询 300 轮）
/perf bench 20000      # 提高轮数减小误差
/perf monitor 120      # 监控 120 秒：期间正常游玩/战斗，结束自动出报告
/perf stats            # 查看埋点统计（需先在模块中接入 global.perfTime）
/perf reset            # 清零埋点
```

结果同时输出到聊天与 `logs/kubejs/server.log` 留档。

埋点接入示例（测量某个 tick 处理器内部两段逻辑）：

```js
PlayerEvents.tick(event => {
    if (!everyTicks(event.player, 20)) return;
    global.perfTime('我的模块-装备扫描', () => { /* 昂贵逻辑 */ });
});
```

### 补记：类过滤器报错修复（2026-10-25 首次进游戏实测时发现）

进世界加载 server_scripts 时报错 `Failed to load Java class 'java.lang.System': Class is not allowed by class filter!`，导致 CONST.js 自第 152 行起全部类定义失效、依赖它的所有脚本失败。已核对 KubeJS 2001 源码确认：内置插件对 `java.lang` 前缀整体 deny（仅白名单放行 Number/String 等），且 `kubejs.classfilter.txt` 只从 mod jar 内部读取，用户侧无法添加放行规则。

修复内容（涉及 4 个文件，均通过 node --check）：

| 文件 | 修改 |
|---|---|
| `server_scripts/CONST.js` | 删除被拒的 `java.lang.System`/`java.lang.Runtime` 加载，新增 `MCUtil = Java.loadClass('net.minecraft.Util')`（`Util.getNanos()` 内部即 `System.nanoTime()`，纳秒精度相同） |
| `server_scripts/system/perf/probe.js` | 4 处 `JavaSystem.nanoTime()` → `MCUtil.getNanos()` |
| `server_scripts/system/perf/bench.js` | 2 处 `JavaSystem.nanoTime()` → `MCUtil.getNanos()` |
| `server_scripts/system/perf/monitor.js` | 计时同上替换；移除 JVM 内存采样与报告项（`java.lang.Runtime` 无允许的替代类，java.lang.management 同被前缀拒绝），报告保留 TPS、实体数、玩家数 |

若进游戏后 `Util.getNanos` 不可用（可能性低，1.20.1 official mappings 已确认存在），兜底方案为 `java.time.Instant.now()`（java.time 前缀未被 deny，微秒精度，微基准可用）。
